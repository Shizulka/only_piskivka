# Порівняльний аналіз: Синхронна та асинхронна комунікація (Лабораторна робота №4)

## 1. Що змінилося порівняно з лабораторною роботою №3?
У Лабораторній роботі №3 ми впровадили принцип CQS, розділивши операції на атомарні Команди (запис) та Запити (читання). Проте виконання всіх дій у межах одного сценарію залишалося лінійним: основна бізнес-логіка та всі супутні побічні ефекти виконувалися послідовно в одному обробнику (Handler).

**У Лабораторній роботі №4 ми змінили архітектуру комунікації:**
* Введено поняття **Інтеграційних подій (Integration Events)** (наприклад, `ReviewCreatedEvent`, `UserRegisteredEvent`).
* Реалізовано **Event Bus (Шину подій)** для оркестрації повідомлень.
* Побічні операції винесено в окремі ізольовані модулі, які тепер виступають як «підписники» (Subscribers) на події ядра системи, а не викликаються напряму.

## 2. Які побічні операції ви виділили і чому?
Для проєкту «Only Piskivka» було виділено допоміжний компонент **Аудиту та логування активності (Audit Component)**.

**Чому саме аудит?**
Створення відгуку або реєстрація користувача — це критичні бізнес-операції. Фіксація цих дій в журналі аудиту (для модерації чи безпеки) є важливою, але *побічною* дією. 
Якщо сервіс логування або його база даних тимчасово недоступні, це не повинно блокувати можливість користувача залишити відгук про заклад. Основна транзакція має бути успішною незалежно від статусу допоміжної системи логування.

## 3. Порівняння синхронного та асинхронного підходів

| Критерій | Синхронна комунікація (Прямий виклик) | Асинхронна комунікація (через Event Bus) |
| :--- | :--- | :--- |
| **Час відповіді API** | **Більший.** Час відповіді клієнту дорівнює сумі часу виконання основної дії та всіх побічних операцій. | **Менший.** API відповідає одразу після виконання основної дії та публікації події в Event Bus. Побічні дії виконуються у фоні. |
| **Поведінка при збоях** | **Жорстка (Fail-fast).** Якщо допоміжний сервіс падає, падає весь запит (наприклад, відгук не створюється). | **Відмовостійка.** Збій у сервісі аудиту не впливає на створення відгуку. Система досягає узгодженості згодом (Eventual Consistency). |
| **Зв'язаність (Coupling)** | **Висока.** Обробник команди жорстко залежить від контракту (інтерфейсу) `AuditService`. | **Слабка (Low Coupling).** Обробник нічого не знає про аудит, він лише повідомляє: «Відгук створено». Підписники реагують автономно. |
| **Складність реалізації** | Низька. Простий імпорт і виклик методу, легко відстежувати стек викликів (Stack Trace). | Висока. Потребує налаштування шини подій та розробки чітких контрактів подій. У контексті модульної структури тестування вимагає суворої ізоляції: у Unit-тестах ми ізольовано перевіряємо публікацію подій (Event Dispatching), мокуючи обробники з повним урахуванням нових шляхів модульного моноліту (наприклад, патчі для обробників тепер націлені суто на `src.modules.core...`), щоб тести одного модуля технічно не зачіпали логіку іншого. |
| **Тестування** | Просте. Легко мокати залежності в Unit-тестах. | Складніше. Необхідно окремо тестувати публікацію події та логіку підписника (Subscriber). |

## 4. Який підхід ви б обрали для production-системи і чому?
Для production-системи «Only Piskivka» наша команда б обрав **асинхронний підхід (Event-Driven Architecture)** для всіх побічних операцій (Аудит, Сповіщення/Email, Аналітика). 

**Обґрунтування:** Платформа відгуків орієнтована на високу доступність для клієнтів. Користувач не повинен чекати або отримувати помилку 500 через те, що сервіс відправки Email або сервер аналітики "завис". Синхронну комунікацію варто залишити **лише для суворих доменних валідацій** (наприклад, перевірка через платіжний шлюз під час оплати, де ми не можемо продовжувати без відповіді).

## 5. Ідемпотентність: Що станеться, якщо одна подія буде доставлена двічі?
В асинхронних системах з брокерами повідомлень (RabbitMQ, Kafka) гарантується доставка "At-least-once" (принаймні один раз). Це означає, що дублювання подій є нормальним явищем через мережеві затримки або ретраї.

**Чи ідемпотентні наші обробники?**
Так, обробники спроєктовані як **ідемпотентні** (повторне виконання не змінює кінцевий стан системи). 
Для забезпечення цього кожна подія (наприклад, `ReviewCreatedEvent`) містить унікальний ідентифікатор `event_id` (UUID). 
* Коли `AuditHandler` отримує подію, він спочатку перевіряє в базі даних, чи існує запис із таким `event_id`.
* Якщо запис вже є — обробник просто ігнорує подію (або повертає статус "Успіх" для брокера).
* Якщо немає — створює новий запис аудиту.
Це гарантує, що подвійна доставка повідомлення не призведе до появи дублікатів у логах системи.
