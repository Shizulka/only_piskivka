# Порівняльний аналіз: впровадження принципу CQS (Command-Query Separation)

Даний аналіз описує результати рефакторингу прикладного шару (Application Layer) нашого проєкту «Only Piskivka» з переходом від сервісної архітектури (Лабораторна робота №2) до архітектурного підходу CQS (Лабораторна робота №3).

## 1. Зміни в структурі проєкту порівняно з лабораторною роботою №2
У попередній лабораторній роботі прикладний шар проєкту (`src/application/`) базувався на великих класах-сервісах (`UserService`, `PlaceService`, `ReviewService`). Кожен сервіс об'єднував у собі абсолютно всі сценарії використання (Use Cases) для певної бізнес-сутності — як операції зміни стану додатка (реєстрація, видалення), так і операції отримання даних.

**Після рефакторингу за принципом CQS структура прикладного шару кардинально змінилася:**
* Класи-сервіси були повністю ліквідовані.
* Папку `src/application/` розділено на два чіткі ізольовані напрямки: `commands/` (запис) та `queries/` (читання).
* Кожен окремий Use Case тепер представлений парою атомарних класів:
  * **Команда (Command)** або **Запит (Query)** — це чисті, незмінні DTO (Data Transfer Objects), які містять виключно вхідні дані для сценарію.
  * **Обробник (CommandHandler / QueryHandler)** — клас, що містить єдиний публічний метод (наприклад, `handle()`), який інкапсулює виконання конкретного бізнес-сценарію.

## 2. Переваги CQS: чим допомогло розділення
* **Ідеальне дотримання принципу Single Responsibility (SRP):** Кожен обробник відповідає лише за один сценарій використання додатка. Код став максимально сфокусованим, його набагато легше читати, підтримувати та рев'юїти.
* **Оптимізація та спрощення шару читання (Queries):** Для запису даних нам життєво необхідний складний домен із фабриками та об'єктами-значеннями (Rich Domain Model) для захисту інваріантів бізнесу. Однак операціям читання доменні правила не потрібні — їм потрібно просто максимально швидко отримати дані з БД. Розділення дозволило запитам обходити доменні фабрики й мапери, трансформуючи дані з БД напряму у плоскі структури відповідей.
* **Гнучкість та чистота тестування:** Тести для команд тепер пишуться як чисті Unit-тести, де ми ізольовано перевіряємо бізнес-правила за допомогою моків. Тести запитів, навпаки, фокусуються на правильності SQL-запитів, фільтрації та сортуванні даних у реальній БД, що робить тестову стратегію більш зрілою.

## 3. Недоліки CQS: що ускладнилося
* **Вибух кількості класів (Class Explosion):** Замість трьох файлів сервісів у проєкті з'явилися десятки нових дрібних файлів (окремо класи Команд, Запитів та їхніх Хендлерів). Це дещо ускладнює початкову навігацію по структурі каталогу для розробників, не знайомих із патерном.
* **Збільшення обсягу шаблонного коду (Boilerplate):** Для кожного Use Case тепер необхідно створювати окрему конфігурацію Dependency Injection (впровадження залежностей) на рівні FastAPI-контролерів, прокидаючи репозиторії індивідуально в кожен Handler.

## 4. Відмінність Command / Query Handler від єдиного Service
* **Клас-Сервіс (Service)** — це процедурний підхід, де клас виступає «контейнером для методів». З розвитком проєкту сервіси неминуче перетворюються на «Божественні об'єкти» (God Objects): вони обростають десятками методів, починають залежати від величезної кількості репозиторіїв та інтерфейсів одночасно, а зміна одного методу ризикує випадково поламати інший код у тому самому файлі.
* **Обробник (Handler)** — це об'єктно-орієнтоване моделювання дії як окремої сутності додатка. Обробник знає лише про свій конкретний Use Case. Він залежить виключно від тих репозиторіїв чи сервісів безпеки, які потрібні для виконання цієї єдиної операції, що мінімізує зв'язність коду (Low Coupling).

## 5. Вплив CQS на розширюваність додатка
* **У сервісній архітектурі** додавання нової функції (наприклад реєстрація користувача) вимагає відкриття файлу `UserService` та дописування туди нового методу. Це порушує принцип відкритості/закритості (Open-Closed Principle), оскільки ми модифікуємо вже протестований та працюючий файл, ризикуючи внести регресійні баги.
* **У CQS архітектурі** додавання нової функції відбувається виключно шляхом створення двох абсолютно нових класів (наприклад, `BlockUserCommand` та `BlockUserCommandHandler`) в новому файлі. Старий працюючий код при цьому залишається фізично недоторканим, що гарантує нульовий ризик регресії для існуючих Use Cases.

## 6. Відмінність структури даних Query (Read Model) від доменної моделі
Структури даних, які повертають наші Query Handlers (Read Models / Response DTO), суттєво відрізняються від чистих доменних сутностей (`Domain Entities`).

**Чому це важливо:**
1. **Захист інваріантів vs Зручність представлення:** Доменна модель (`User`, `Place`) спроєктована навколо бізнес-логіки системи. Вона інкапсулює приватні поля та складні об'єкти-значення (наприклад, `TimeRange` чи `Email`), які незручно серіалізувати напряму в JSON.
2. **Денормалізація для клієнта:** Фронтенду (клієнту) для відображення списку відгуків часто потрібен плоский об'єкт, який містить і текст відгуку, і назву закладу, і юзернейм автора. У доменній моделі це три різні пов'язані сутності. Query Handler дозволяє зробити оптимізований SQL-запит із `JOIN`, витягнути лише потрібні текстові поля і змапити їх одразу в денормалізоване плоске DTO відповідальності шару представлення. Це повністю позбавляє систему накладних витрат на побудову та мапінг важких доменних графів об'єктів там, де потрібно просто прочитати текст.
