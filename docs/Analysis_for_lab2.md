# Порівняльний аналіз: перехід від CRUD до шарової архітектури

Даний аналіз описує процес рефакторингу нашого проєкту «Only Piskivka» від базового CRUD-підходу, який в Лабораторній роботі №1 до структурованої шарової архітектури який в Лабораторній роботі №2.

## 1. Зміни в структурі проєкту порівняно з лабораторною №1
У першій лабораторній роботі проєкт мав «плоску» структуру, де межі між відповідальностями були розмиті. Бізнес-логіка (валідація, обробка помилок) часто знаходилася безпосередньо в контролерах або сервісах, які мали пряму залежність від моделей бази даних (SQLAlchemy).

**Після рефакторингу проєкт розділено на 4 незалежні шари:**
* **Domain (Домен):** Ядро системи. Тут знаходяться «чисті» сутності (`User`, `Place`, `Review`), об’єкти-значення (`Email`, `TimeRange`) та інтерфейси репозиторіїв. Цей шар не має жодних зовнішніх залежностей.
* **Application (Прикладний шар):** Містить сервіси (Use Cases), які оркеструють логіку домену та взаємодію з інфраструктурою.
* **Infrastructure (Інфраструктура):** Реалізація репозиторіїв, робота з ORM, схеми Pydantic та мапери для перетворення даних між БД та доменом.
* **Presentation (Представлення):** API-контролери FastAPI, що відповідають за HTTP-запити та повернення відповідей.

## 2. Переваги розділення на шари
* **Ізоляція бізнес-логіки:** Тепер доменні правила (наприклад, перевірка коректності імейла або часового діапазону) захищені від змін у фреймворку чи базі даних.
* **Покращена тестованість:** Ми отримали можливість писати чисті Unit-тести для домену, які запускаються миттєво без підняття PostgreSQL чи сервера.
* **Чітка відповідальність:** Кожен компонент системи тепер має одну чітку роль, що спрощує читання та підтримку коду.

## 3. Гнучкість зміни БД або фреймворку
Завдяки дотриманню принципу інверсії залежностей (DIP), зміна технологічного стеку стала значно простішою:
* **Зміна бази даних:** Оскільки прикладний шар залежить від інтерфейсу `UserRepositoryInterface`, ми можемо замінити PostgreSQL на будь-яку іншу БД (наприклад, MongoDB), просто написавши нову реалізацію репозиторію в шарі Infrastructure.
* **Зміна фреймворку:** Логіка додатка не залежить від FastAPI. Якщо ми захочемо перейти на Flask або Django, шар `Domain` та `Application` залишаться абсолютно незмінними.

## 4. Обґрунтування вибору моделі домену
Для проєкту було обрано **Rich Domain Model (Багата модель домену)**.
* **Обґрунтування:** У нашому проєкті сутності самі захищають свої інваріанти. Наприклад, сутність `Review` у методі `__post_init__` сама перевіряє свій контент. Якщо відгук порожній, об'єкт просто не буде створено. Це гарантує, що система працює лише з валідними бізнес-об'єктами на рівні ядра, що надійніше за анемічну модель, де логіка розпорошена по сервісах.
